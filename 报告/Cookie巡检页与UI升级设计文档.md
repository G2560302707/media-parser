## 第一部分 · Cookie 能力全景（巡检页的数据基础）

### 1.1 现状链路（已验证，无需改造）

```
后台设置页保存 → system_settings 表 cookie_{platform}
                      ↓ 优先级 1
解析请求 → ParserFactory.create_parser()（每请求新建实例）
        → parser.__init__ → get_platform_cookie() 实时读取
                      ↓ 兜底 2/3
        环境变量 DOUYIN_COOKIE / 别名 DY_COOKIE …
```

**结论：配置保存即生效，无需重启**（[cookie_manager.py:25](../src/utils/cookie_manager.py#L25)、[admin.py:151](../src/web/admin.py#L151)）。巡检页要做的不是打通配置链路，而是把"配了没配、还有没有效"变成可见、可验证、可操作。

### 1.2 能力门控全景表（源：docs/parsers/* + 代码 + 本次实测）

| # | 配置键（别名） | 平台 | 门控能力 | 强制度 | 失效时的表现 |
|---|--------------|------|---------|--------|-------------|
| 1 | `DOUYIN_COOKIE`（+`DOUYIN_UIFID`） | 抖音 | 实况动轨 `live_photo_url`；放映厅长片 `/lvdetail/`；短剧合集 | **强制**（用这些能力时） | **静默降级**：仍返回 200+静态图，无告警（实测确认，Argus 403 后走 SSR） |
| 2 | `YUANBAO_COOKIE`（=`WECHAT_CHANNELS_COOKIE`） | 视频号 | **整个平台**：无水印视频/标题/图集（走元宝代理换 token） | **强制** | 平台整体不可用，返回 `WECHAT_CHANNELS_COOKIE_REQUIRED` |
| 3 | `PINDUODUO_COOKIE`（=`PDD_COOKIE`） | 拼多多 | 多多视频（feed_id）；商品图文不需要 | 强制（用视频时） | 返回 `PINDUODUO_COOKIE_REQUIRED` |
| 4 | `DOUBAO_COOKIE` | 豆包 | 视频无水印**原画**（original_media_info 解密直链） | 增强 | 有视频但是带水印预览切片 |
| 5 | `XHS_COOKIE`（=`XIAOHONGSHU_COOKIE`） | 小红书 | 风控兜底：服务器 IP 匿名抓取易被 302 到登录页；配置后成功率 99%+ | 建议 | 高频/机房 IP 下 `XIAOHONGSHU_COOKIE_REQUIRED`；家宽/低频实测免 Cookie 全过 |
| 6 | `KUAISHOU_COOKIE`（=`KS_COOKIE`） | 快手 | 风控兜底：触发反爬（`result: 2`）时启用 | 按需 | 返回 `KUAISHOU_COOKIE_REQUIRED` |
| 7 | `WEIBO_COOKIE` | 微博 | 机房 IP / 高规格视频（常规内容自动生成访客会话） | 可选 | 降级为访客通道 |
| 8 | `JIMENG_COOKIE` | 即梦AI | 请求增强（附加 appid/device-platform 头） | 可选 | 部分接口成功率下降 |
| 9 | `YUANBAO_COOKIE`（复用） | 腾讯元宝 | 公开分享免 Cookie；独立分享页接口受限时复用 | 可选 | 接口受限 |

> 洞察：9 个配置键里只有 **1 个（视频号）是"不配就全平台瘫痪"**，1 个是"静默失效最危险"（抖音实况，正是上次测试集实测暴露的 P1 问题），其余多为增强/兜底。巡检页的视觉权重应按此排序。

### 1.3 探针方案（主动巡检核心设计）

每个平台的探针 = **金丝雀链接 + 判定信号**，并采用**双跑对照法**区分"Cookie 失效"与"链接失效"：

> 同一条金丝雀链接跑两次解析：带当前 Cookie 一次、强制无 Cookie 一次（解析器已支持免 Cookie 通道）。两次都失败 → 链接失效（不怪 Cookie）；带 Cookie 成功、无 Cookie 失败/降级 → Cookie 有效且增益明确；带 Cookie 失败但无 Cookie 成功 → **Cookie 已失效**（最强的失效信号）。

| 平台 | 金丝雀样例 | 判定信号 | 附加字段校验 |
|------|-----------|---------|-------------|
| 抖音 | 一条实况链接（可复用测试集 `ZtiyRAA2JLs` 类样例） | `live_photo_url` 存在 = 有效；缺失 = 失效/降级 | `sessionid_ss`、`passport_csrf_token`、`odin_tt` 存在；`UIFID` 可提取（Cookie 内或 `DOUYIN_UIFID`） |
| 视频号 | 一条视频号分享链接 | `video_url` 非空 = 有效 | `hy_user`、`hy_token` 存在 |
| 拼多多 | 一条 feed 视频 | 错误码 ≠ `PINDUODUO_COOKIE_REQUIRED` = 有效 | `PDDAccessToken` 存在 |
| 豆包 | 一条视频分享 | 返回原画直链（非水印预览）= 有效 | `sessionid_ss` 存在 |
| 小红书 | 一条图文笔记 | 非 302→/login、非 `XIAOHONGSHU_COOKIE_REQUIRED` = 有效 | `a1` 或 `web_session` 存在 |
| 快手 | 一条常规视频 | 解析成功 = 有效（兜底型，被动为主） | — |
| 微博 | 一条高规格视频 | 解析成功 = 有效 | — |
| 即梦 | 一条生成记录分享 | 解析成功 = 有效 | — |

金丝雀链接存 DB（巡检页可改），不硬编码 —— 链接自带时效，页面必须让管理员能换。

## 第二部分 · 巡检页设计

### 2.1 定位

- **这一屏回答的唯一问题**：「现在哪些能力因为 Cookie 处于未配置或失效状态？」
- **高频动作**：看到红色/黄色 → 点"验证"或"去配置" → 保存 → 复验。全流程 3 次点击内。
- 归属：管理台新导航项「凭据巡检」，位于「平台开关」与「调用日志」之间（凭据是平台级配置的延伸）。

### 2.2 页面结构（1440 宽，ASCII 线框）

```
┌──────────────────────────────────────────────────────────────────────┐
│ Cookie 凭据巡检                                    [3 分钟前巡检 ⟳]    │  h1 24px/600
│ 3 项配置有效 · 1 项疑似失效（抖音实况已降级 6 天）· 2 项未配置            │  副行 = one finding
│                                            [ 全部重新巡检 ]  ← 唯一主按钮│
├──────────────────────────────────────────────────────────────────────┤
│ 状态总览（一个容器，1px 竖线分隔 4 格，不是 4 张卡片）                     │
│   有效 4        疑似失效 1      未配置 2       增益型 2                  │  值 24px tabular
│   配置于 10-02   抖音          视频号/拼多多   微博/即梦                  │  标签 12px 灰
├──────────────────────────────────────────────────────────────────────┤
│ 凭据明细（主区块 = 签名元素：能力覆盖矩阵）                                │
│                                                                       │
│  平台      来源    覆盖能力              状态      最近验证   操作        │
│  ──────────────────────────────────────────────────────────────────── │
│  抖音      数据库   视频·图文 ✓ 实况 ✗ 放映厅 ✗   ● 疑似失效  10-22 14:20 │ 验证 配置
│  视频号    —       整平台（未解锁）          ○ 未配置     —          配置   │
│  小红书    环境变量 视频·图文·实况 ✓（兜底）   ● 有效     10-28 09:30 │ 验证   │
│  豆包      数据库   图文·音乐 ✓ 视频 ✗ 水印     ● 有效     10-28 09:30 │ 验证   │
│  …（9 行，按强制度排序：强制 → 增强 → 兜底）                               │
├──────────────────────────────────────────────────────────────────────┤
│ 巡检历史（近 7 天，每平台一条 2px 状态带 + 失败原因，抽屉展开）             │
└──────────────────────────────────────────────────────────────────────┘
```

关键设计决定（依据 app-screens 研究）：

1. **状态总览是一个容器分格，不是 KPI 卡片阵列** —— 研究中 0/23 屏在 KPI 上放图标圆底；数字即界面。
2. **主区块 = 平台 × 能力覆盖矩阵**，这是本产品独有的东西（50 个平台的凭据体系），也是页面的"签名元素"。"覆盖能力"列用 `✓/✗/—` 文字与灰度 chips，**不用彩色图标**；只有"状态"列带色。
3. **副行（one finding）讲具体的事**：「抖音实况已降级 6 天」比「1 项异常」可信十倍。数据来自最近一次探针记录。
4. **最常见动作一击可达**：行内「验证」（发探针）、「配置」（行内展开编辑，见 2.4）。
5. **按强制度排序**：强制（视频号、拼多多视频、抖音实况）永远在最上面 —— 未配置的强制项是页面最重要的事。

### 2.3 状态机与判定

```
未配置 not_configured ──配置──► 验证中 probing ──┬─► 有效 healthy
                                              ├─► 疑似失效 stale（对照法判定）
                                              ├─► 探针失败 probe_failed（链接/网络）
                                              └─► 字段缺失 incomplete（缺 sessionid 等必需字段）
```

- **字段校验**（秒级、零网络）与**真实探针**（3-10 秒）分离：保存 Cookie 时立刻做字段校验并即时反馈，真实探针异步跑。
- **被动巡检**（零成本增益）：`record_request` 调用日志已有平台级错误码 —— 近 24h 内某平台连续出现 `*_COOKIE_REQUIRED` 错误 → 自动置为"疑似失效"，无需等定时探针。这是本项目独有的免费信号，必须用。
- **自动巡检**：后台守护线程每 6 小时跑一轮字段校验（不做全量真探针，避免消耗目标平台风控配额）；真探针只手动触发或被动信号触发。
- 失效不弹全局告警横幅；红色只出现在该行状态 pill 与副行文字里（"Red is a signal, not a texture"）。

### 2.4 后端设计

```
GET  /admin/cookies/overview        各平台：配置来源(DB/env/无)、字段完整度、
                                    当前状态、最近验证时间、近24h被动信号、覆盖能力矩阵
POST /admin/cookies/probe           body: {platform} → 同步探针(超时60s)或异步+轮询
POST /admin/cookies/probe-all       全量（串行，平台间 2s 间隔，降低风控压力）
POST /admin/cookies/canary          修改某平台金丝雀链接
POST /admin/settings                保存 Cookie —— 复用现有路由，保存后触发字段校验
GET  /admin/cookies/history/{key}   巡检历史记录
```

- 新表 `cookie_probe_records(id, platform_key, status, detail_json, duration_ms, probed_at)`。
- 探针实现复用 `_resolve_and_fetch` 的解析链路（对照跑通过临时屏蔽 `cookie_{platform}` 设置实现"强制无 Cookie"）。
- 配置行内编辑：展开行内 textarea + 保存，调现有 `POST /admin/settings`（AJAX 分支已存在），保存后自动触发该平台字段校验 + 建议探针。**不做跳页**。

### 2.5 视觉规范（本页专项）

沿用现有 Tailwind + brand 体系，以下为本页的"决定清单"：

| 决定 | 值 |
|------|-----|
| 状态色 | 严格三组 pale pill：有效 `#dcfae5/#04250e`、失效 `#ffedea/#831c1e`、警示 `#fffbeb/#92400e`；未配置=灰色描边 chip（中性状态不带色） |
| 色彩预算 | 彩色像素 ≤5%：只有状态 pill、探针进行中的 spinner、主按钮 |
| 主按钮 | 每页一个：「全部重新巡检」，用近黑 `#1d1f20`（研究中 12/23 主按钮近黑而非品牌色；brand 靛蓝仅保留给现有导航高亮） |
| 数字 | 全部 `font-variant-numeric: tabular-nums`，右对齐；日期 ISO `2026-10-28` |
| 边线 | 卡片 1px `#e8e8e8`，行分隔线更浅一档 `#f2f2f2`，无阴影（浮层除外） |
| 行高 | 明细行 48px（单行）+ 展开态；历史行 44px |
| 禁入 | 图标圆底、渐变、卡片阴影、斑马纹、大写字母间距标签、入场动画 |

**动效 = 纯反馈层**（管理台不做入场动画，这是研究结论不是保守）：

- 行 hover：1px 轮廓 6px 圆角外扩 1px（150ms ease-out）
- 状态切换：pill 颜色 200ms 过渡 + 探针进行中该行显示**扁平灰条骨架**（保持行高不变，无 shimmer 渐变）
- 探针完成：状态 pill 从"验证中"翻转为目标态，无弹跳无缩放
- 全部包 `prefers-reduced-motion` 降级
- 仅用 `transform/opacity`，禁重排属性

## 第三部分 · UI「高级感」升级 —— ShortcutHub 方案借鉴映射

先说一个必须点破的错位：ShortcutHub 文档是 **Vue 3 + Element Plus** 生态写的，而本项目是 **Flask + Jinja + Tailwind CDN**（无前端框架）。所以"借鉴"的正确方式不是搬库，是**搬判断**——它六个注意事项全部照单吸收，工具层逐个翻译成无框架等价物。

### 3.1 逐项映射表

| ShortcutHub 用了 | 对本项目的判断 | 替代/落地方式 |
|---|---|---|
| `motion-v`（Vue 动画库） | ❌ 不适用（依赖 Vue） | CSS transition + Web Animations API；页面切换用 **View Transitions API**（Chrome/Edge 原生，`@view-transition { navigation: auto }` 一行启用，渐进增强） |
| `@vueuse/motion` `v-motion` 入场 | ⚠️ 仅限 `landing.html` / 门户首页 | 原生 `IntersectionObserver` + 8 行 CSS（`opacity/y24 → 1/0`，once 触发）；**管理台禁用入场动画**（见 3.2） |
| `gsap` + `split-type` Hero 逐字+视差 | ✅ 吸收，但只用于 `landing.html` | CDN 引 gsap core + ScrollTrigger（约 70KB gzip，营销页可接受）；管理台一律不引 |
| `lenis` 平滑滚动 | ✅ 仅 `landing.html`，管理台明确禁止（ShortcutHub 自己也这么警告；管理台有表格固定表头/内滚区） | 同其注意事项第 4 条 |
| `lucide-vue-next` 图标 | ⚠️ Vue 包不适用，但**换图标是"观感提升最大一步"的判断成立** | Lucide 官方静态 SVG sprite（构建期生成一份 `icons.svg`，页面 `<use href="#icon-x">`；项目已有 `static/icons.svg` 惯例）。stroke 1.5px、16px、灰色 —— 与研究数据吻合（14/16 屏 outline 1.5px） |
| Element Plus 主题变量覆盖 | ➖ 不适用 | 对应物 = 已有 `tailwind.config` brand token + `console.css`；升级方向见 3.3 token 校准 |
| 六条注意事项 | ✅ 全部吸收 | transform/opacity、prefers-reduced-motion、按需引入、Lenis 限营销页、不引第二套组件库、先易后难 —— 逐条翻译进本项目 |

### 3.2 「高级感」的正确分层（本次设计最重要的判断）

ShortcutHub 把高级感寄托在动效上；但那套研究数据（23 个真实产品屏）给出的是相反结论——**管理后台的高级感来自数据可信与克制，营销页的高级感才来自动效**。所以本项目拆两层：

**A. 管理台 = 质感层（改"决定"，不改"装饰"）**

按影响力排序（这是 skill 给出的"最小风险最大效果"顺序）：

1. **排版**：全局校准为 4 级字阶 `12/14/16/24`（现管理台混用了过多中间尺寸）；数字全部 tabular-nums；标题 24px/600 上限（不出现 32px+）
2. **色彩**：文字三层（`#111 / #5f6368 / #6b6b6b`，全部 ≥4.5:1）；边线三阶（卡片 `#e8e8e8` / 行线 `#f2f2f2` / 控件 `#d1d5db`）；彩色只给数据与状态
3. **状态诚实**：零打印为零、缺值打灰色 `—`、加载=保持布局的扁平灰条（无 shimmer）、错误在出错的卡片内一句话+重试
4. **对齐**：一行一个右缘；卡片同排同底边；网格算术闭合（写得出 `3×372+2×16=1148` 这种等式）
5. **反馈动效**：hover/focus/骨架/View Transitions，仅此四类

**B. landing.html / 门户 = 表现层（ShortcutHub 原方案可基本照搬）**

- GSAP ScrollTrigger Hero 视差 + split-type 逐字入场 + Lenis 惯性滚动 + IntersectionObserver 批量入场
- 这是 ShortcutHub 清单里 ④⑤ 两步的原样落地，连 `prefers-reduced-motion` 包裹方式都相同

### 3.3 一个品牌决定需要明示

skill 研究中 violet/indigo 属"慎用色"（10/23 真实产品屏仅用作单一数据色）。但本项目 brand 靛蓝 `#4f46e5` 已是既有体系 —— **保留品牌色**（仅导航高亮与既有主色位），新页面主按钮用近黑，状态色用上文三组 pale pill。这是"保留品牌资产"的标准处理，记录在案。

## 第四部分 · 落地顺序（先易后难）

| 阶段 | 内容 | 工作量预估 |
|------|------|-----------|
| ① | 管理台 token 校准（字阶/三阶灰/边线/tabular-nums）+ Lucide sprite 替换图标 | 半天 |
| ② | 巡检页骨架：overview API + 状态总览 + 明细矩阵 + 字段校验（零网络探针先行） | 1 天 |
| ③ | 真实探针（双跑对照法）+ 金丝雀配置 + 巡检历史 + 被动信号接入 | 1-2 天 |
| ④ | 行内编辑打通 + 自动巡检线程 + View Transitions | 半天 |
| ⑤ | landing.html 表现层（GSAP + split-type + Lenis + IO 入场） | 1 天 |

## 待确认项

1. 抖音金丝雀实况链接会随作品删除而失效 —— 是否由你定期换，还是巡检页提供"探针失败≠Cookie 失效"的免责提示即可（推荐后者，双跑对照已能自动区分）。
2. 真探针会真实消耗目标平台请求配额（尤其抖音 Argus 风控敏感）—— 默认仅手动触发 + 被动信号触发，是否需要再加频率上限？
3. 阶段⑤ 是否本期内做（营销页动效与巡检页无耦合，可独立排期）。
